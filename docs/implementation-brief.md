## Core formalism
A typed, attributed, source-grounded temporal hypergraph. Separate six layers:
1. Source: conversations, participants, immutable message/excerpt text and anchors.
2. Content: concepts, claims, questions, hypotheses/models, methods, examples, goals, references.
3. Argument/semantic relations: support, challenge, depends_on, distinguishes, reframes, motivates, answers, exemplifies, candidate_for, part_of, related_to, supersedes. Relations are reified, have IDs and provenance; later relations may target a relation for undercutting. Endpoint signatures must be documented and validated.
4. Inquiry moves: typed activities with actor, inputs, outputs, grounding, ordered occurrence. A move can consume or produce multiple nodes (hyperedge). Types include ask, clarify, distinguish, challenge, retract, hypothesize, generalize, deduce, test, reframe, decompose, connect, scope, summarize, propose. Do not claim these are exhaustive psychological primitives. Optional inference family induction/abduction/deduction/unspecified is a tag, not a mandatory trichotomy.
5. Actor-relative stance events and inquiry-status events. Stance is NOT a global node truth status. Positing, endorsing, questioning, rejecting, suspending, retracting are different. A question being answered is NOT equivalent to resolved. Question status open/answered/resolved/deferred/superseded/reopened is separate from semantic kind. Record successive events, don't overwrite history.
6. Extraction/review provenance: explicit vs inferred annotation, proposed/confirmed/rejected interpretation, run metadata (model/provider/prompt/schema version). Extraction confidence is not probability a claim is true. Graph 'coherent' means schema/references/grounding/type/temporal consistency, NOT that every proposition is mutually consistent or true.

Use Pydantic v2 as the executable contract and generate committed JSON Schema; NetworkX for graph operations. JSON is canonical and Git versions it; no database server, frontend framework, vector DB, TypeDB deployment, or custom agent framework required for V1. Relations have role-labelled endpoints so a future TypeDB mapping is possible. Document a correspondence, not a false claim to AIF/PROV conformance. Prefer a simple library plus argparse CLI `inquiry-graph` (short alias `ig` optional).

### Graph data model
Use a top-level Graph with schema_version, id, conversations (embedded sources), nodes, relations, moves, stance_events, question_events, extraction metadata/notes. Content nodes have id, kind, text/label, nonempty anchors. Every relation/move/stance/question event has its own id, anchors, extraction origin explicit|inferred, and review status proposed|confirmed|rejected. Inferred is default unless text explicitly states the relation. Anchor = message_id,start,end,quote; start/end are half-open Unicode character offsets into exact source message text. Find anchors programmatically from quote, never trust guessed offsets. An ambiguous duplicate quote requires an explicit occurrence selector; nonexistent quote is an error. IDs must be stable and globally unique within graph; source IDs namespaced by conversation. Graph may include contradictory statements without inconsistency explosion.

StanceEvent: actor_id,target_id,stance,at_message_id,anchors,origin,review_status. QuestionEvent: question_id,status,actor_id,at_message_id,answer_ids list,anchors,origin,review_status. Resolved requires evidence-bearing answers or an explicit resolution basis; no auto-resolution because assistant answered. Views default exclude rejected annotations and expose proposed vs confirmed. User beliefs are drawn only from user-authored stance evidence; assistant suggestions are never silently attributed to user. A collapsed single-voice view may hide lanes, never erase attribution.

Move: id,kind,actor_id,input_ids[],output_ids[],at_message_id,after_move_ids[] (optional),anchors,origin,review_status. Check ordering in a conversation and acyclicity of after/supersedes only, not entire reasoning graph: substantive feedback loops/dependency cycles are allowed and surfaced. Fail dangling IDs, actor/source mismatch for explicit attribution, malformed offsets, invalid kinds/roles, duplicated IDs, impossible order, status on wrong type. Inputs may target relation IDs for challenging warrants. Keep logic simple and testable.

## Pipeline / CLI
1. import ChatGPT export or normalize provided JSON into source conversation(s).
2. prepare: build schema-constrained extraction prompt and JSON Schema using immutable source IDs. Transcript is untrusted data, never instructions. The LLM returns candidates only; never executes tools/code.
3. extract: implement an actual off-the-shelf provider adapter (prefer direct official OpenAI SDK with Pydantic structured output if suitable; model must be specified, no made-up latest model; no keys created or printed; use environment only) AND response-file mode for a JSON candidate generated by any LLM, enabling this session's installed coding agent as an extraction source. Document truthfully which is live-tested vs mocked. Handle refusal, truncation, schema error, transport error without writing invalid canonical graph. Save model output and validation diagnostics to a quarantine/run folder on failure. No automatic retries with unbounded cost. Do not require paid calls for tests/demo. If LangExtract is not primary, document that it supplies source-span extraction, not full global graph consistency; offer optional import of grounded LangExtract mention output only if small. Don't pretend it solves graph typing.
4. validate: machine-readable report + nonzero exit on hard errors. Schema alone insufficient: cross-reference, provenance, signature and temporal checks.
5. merge: deterministic union across conversation graphs; same ID same content idempotent, same ID differing content rejected; do not silently fuzzy-merge beliefs or similar claims. Exact identity decisions explicit. Candidate same-as proposals can remain unmerged; don't implement speculative ontology alignment.
6. query: stats, open questions (latest actor/context-aware events with visible source/review status), trace node (sources, relation neighbors, move inputs/outputs, stance history), conflicts and dependencies. Dependency cycles reported without falsely declaring entire graph invalid.
7. export: Mermaid Markdown (safe generated IDs/escaped labels), Graphviz DOT and a readable Markdown report. Include a small existing-library self-contained interactive HTML graph (pyvis optional or other off-the-shelf library) if straightforward; no CDN/network required to inspect private graph; HTML escaping/XSS tests. Distinguish content and move nodes so reasoning history is visible, not just a generic concept graph.

## Important semantic corrections for this conversation
Do NOT canonize earlier assistant overclaims as truths: (a) stable/nonadversarial world alone is not a sufficient statistical generalization theorem; need sampling/stationarity etc. (b) recognizing a relational feature entailed by a fully described finite dot configuration need not be logically ampliative, although cognitively useful; no new Shannon information from deterministic processing alone. (c) induction/abduction/deduction exhaustiveness remains unproved; induction need not always come first. (d) Bayesian updating does not independently justify model/prior/likelihood choices. (e) dialogical reconstruction describes expressed reasoning, not access to hidden mental processes. (f) distinctions between physical, measurement, representation, inference, metacognition, communication are modeling choices and cross-linked, not proven strata of nature. These corrections are analyst notes, not things the user explicitly endorsed.
